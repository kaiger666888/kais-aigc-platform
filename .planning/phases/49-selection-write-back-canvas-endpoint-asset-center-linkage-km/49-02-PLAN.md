2. **open review 查询**：`GET /api/v1/reviews?status=&type=&source=&priority=&sort=&cursor=&limit=`（reviews.py:239-300）。**无 content_ref 过滤参数**——content_ref 匹配必须拿 items[] 客户端过滤。响应 envelope：`{ data: { items: ReviewResponse[], next_cursor, has_more } }`。ReviewResponse 字段：id/type/content_ref/metadata/source_system/priority/risk_score/state/disposition/callback_url/version/created_at/updated_at（schemas.py:182-197）。
3. **kmc 提交形状**：source_system="kais-movie-agent"；content_ref=`f"{episode_id}/{gate.config.phase}"`（runner_hooks.py:338，如 "ep03/p11a0"）；type=gate_id。
4. **`chosen_variant_id`/`suggested_action` 在 review-platform 全仓不存在**（grep 全 app/ 零命中）——approve 的 result.selected 不产生这两个字段；它们也进不了 GET 响应、回调体（workers/tasks.py:362-369 回调体仅 {review_id, old_state, new_state, timestamp, source_system, disposition, result}，缺 kmc resume_from_callback 必需的 gate_id/decision → 回调路径对 kmc 是死路）。
5. **kmc 轮询现实**（runner_hooks.py:640-678 Path 2）：query_review_status 只提取 `{review_id, state, disposition, version}`（review_platform.py:292-309）；轮询判定 `state in {"resolved","closed"}` 而 platform 状态词汇是 PENDING/POLICY_EVAL/APPROVING/COMPLETE（schemas.py:27-38）——**永不匹配**。因此 kmc 30s 轮询在现版本读不到任何 platform 侧 resolve（连 decision 都读不到，不止 chosen_variant_id）。
6. **`_chosen_from_suggested` 格式（已验证）**：runner_hooks.py:612-615 —— `action.startswith("choose:")` → 返回 `action.slice("choose:".length).trim()`；即 `choose:<variant_id>` 前缀格式。kmc 侧唯一能把 chosen 带出来的入口，但其输入 suggested_action 在 platform 侧无来源。
7. **结论（写入桥接模块头注释 + SUMMARY）**：D-11 冻结双仓库下，SC-4 的 "kmc 30s 轮询读到" 在本 phase 不可达——这是**消费侧协议缺口**（state 词汇 + client 字段提取），不是 kap 桥接能力缺口。桥接按第 1-3 条真实契约实现并落 choose:v{N} 标记（result.selected 是 platform 唯一机器可读的选定通道，comment 是唯一自由文本通道）；当 kmc/platform 未来对齐（out of scope）时桥接无需改动即点亮。
