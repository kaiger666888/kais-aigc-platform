<objective>
Phase 46 Wave 2 — the E2E test (VERIFY-03). Marked `autonomous: false`
because it requires docker-compose v9 running + manual decision to opt
in via `PHASE46_RUN_E2E=1`. The master `verify:phase-46-contracts`
(from Plan 01) deliberately excludes this script — operators must run
it explicitly when they're ready to spend the GPU cycles.

The E2E test exercises the receiver-side flow:
1. Drop a known-good p04 fixture manifest into a test project's OSS dir
2. Trigger canvas_sync (via the subscriber — same code path production uses)
3. Poll GET /api/v2/canvas/nodes
4. Assert every node has description ≥ 20 chars AND at least one of
   {archetype, role, era} (per Phase 42 contract + Phase 44 import
   stamping + Phase 45 UI rendering)

What this catches that the static scripts (Plan 01) don't:
- canvas_sync integration bugs (manifest → HTTP POST → canvas state)
- Relational store write path (canvas_nodes table)
- API GET handler (nodes.ts)
- End-to-end params forwarding through the actual subscriber

What this does NOT catch (out of scope per CONTEXT.md D4):
- ComfyUI render correctness
- LLM script generation quality
- Real creative-pipeline timing / GPU scheduling

Output: 1 new env-gated script + 1 fixture + 1 npm script entry (NOT
in the master verify chain). VALIDATION.md gains a "Manual E2E"
section.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Script → docker daemon | spawnSync against `docker` CLI; inherits dev permissions |
| Script → filesystem (OSS dir) | Writes to a test project's OSS dir; cleanup on success |
| Script → canvas API (localhost) | HTTP GET against a known-bounded endpoint; no auth in dev (matches existing canvas routes) |
| Script → python3 subprocess (canvas_sync trigger) | Same trust level as Plan 01's VERIFY-01 pytest spawn |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-46-05 | Tampering | Attacker sets PHASE46_OSS_DIR to sensitive path | mitigate | Default is repo-local data/oss/e2e-test/; dev/CI-only env var; documented as manual |
| T-46-06 | DoS | E2E test runs against prod canvas API | mitigate | Default API port is localhost:3000 (dev). Production deployments must NOT set PHASE46_RUN_E2E=1 in CI |
| T-46-07 | Info Disclosure | E2E test creates synthetic nodes in shared canvas | accept | Test project ID defaults to 1 (typically a dev sandbox); fixture uses synthetic names ("角色 测试-01"); script cleans up on success |
| T-46-08 | Repudiation | Test failure leaves fixture in OSS dir | accept | Documented in VALIDATION.md; operator cleans up manually; the fixture file itself is non-sensitive |
| T-46-09 | Tampering | canvas_sync CLI invocation path varies by environment | accept | Script has fallback paths + checkpoint mechanism; operator triggers manually if subprocess path fails |
| T-46-SC | Tampering | npm installs | accept | Plan 02 introduces zero new packages |

Security net effect: Plan 02 is env-gated + dev-only by default. The auto-skip behavior means accidental invocation in CI is harmless. The fixture is synthetic + cleaned up on success.
