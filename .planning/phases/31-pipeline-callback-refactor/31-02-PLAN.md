<objective>
Refactor the two callback files that export phase constants (`phase-complete.ts` exports `REVIEW_REQUIRED_PHASES` + `PHASE_INGEST_MAP`; `resume.ts` exports `PHASE_ORDER`) so they instead consult the skill registry at runtime. Delete the constant exports entirely. Both files must resolve the active skill_id from the `kv_pipelineRun` row (falling back to `"movie-v1"` with a `console.warn` when null), look up the phase declaration via `registry.phaseById(skillId, phase)`, and handle the "skill not registered" case with a 500 error.

Purpose: This is the core of the Phase 31 refactor — the callback hot path stops reading hardcoded constants and starts asking the registry. Per CONTEXT.md decision "Registry is source of truth (Architecture Pattern 3): delete hardcoded constants, do not wrap." The PHASE_INGEST_MAP export is deleted because it was descriptive metadata never consulted at runtime in this file (the runtime ingest branching on `outputs[].type` is unchanged).

Output: Two rewritten callback files with registry lookups, zero constant exports, and proper skill-not-registered error handling.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| external caller → callback endpoint | Untrusted request body crosses into the handler. Existing validateFields middleware validates pipelineId/projectId/phase/status shapes. |
| callback → registry | The handler reads skill_id from the DB row (server-controlled) and looks it up in the in-memory registry (server-controlled). No user input reaches the registry lookup key directly. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-31-03 | Information Disclosure | console.warn on null skill_id | accept | The warn message includes the pipelineId (a server-generated ID, not PII). This is internal API logging for operator debugging. v1.6 assumes trusted internal network per CONTEXT.md deferred items (auth on submit-to-review is deferred). Acceptable for v1.6. |
| T-31-04 | Denial of Service | registry.get + phaseById on every callback | accept | Both are O(1) Map lookups (Phase 29 registry design). No SQL, no scan. Negligible overhead vs. the existing DB writes in the handler. |
| T-31-05 | Tampering | skill_id column on kv_pipelineRun | accept | The skill_id is set by the pipeline initiator (Phase 33 compliance) and read server-side. A callback caller cannot inject a skill_id — it comes from the DB row, not the request body. The 500 "skill not registered" error surfaces any tampering attempt loudly. |
| T-31-06 | Information Disclosure | 500 error message reveals skill_id | mitigate | The error message `skill '<id>' not registered` includes the skill_id from the DB row. This is intentional — operators need the ID to diagnose a dropped registry row. The skill_id is not sensitive (it's a public manifest identifier like "movie-v1"). No PII. Acceptable for internal API. |
