Use `.strict()` is REQUIRED, not optional.

    - `asset_categories`: `z.array(z.object({ id: z.string(), label: z.string() }).strict())`
    - `review_criteria`: `z.object({ auto_threshold: z.number(), human_threshold: z.number() }).strict()`
    - `engine_task_types`: `z.array(z.string())`
    - `runtime`: `z.object({ type: z.enum(['external-http','in-process']), endpoint: z.string().optional(), healthcheck_path: z.string().optional(), callback_url_template: z.string().optional() }).strict()`

    Apply `.strict()` on every nested object schema, not just the root — defense in depth against typos at any level.

    Add custom validation rules via `.refine()` or `.superRefine()` on the root schema (or as a post-parse step inside validateManifest). These encode the four contract invariants where they cannot be expressed by built-in zod checks:

    1. VERSION FORMAT rule (ruleId: 'MANIFEST_VERSION_FORMAT'): version must match the regex `^\d+\.\d+$` (major.minor only, no patch, no leading 'v'). Examples: '1.0' valid, '2.5' valid, '1.0.0' invalid, 'v1' invalid, '1' invalid.

    2. NODE ID NAMESPACING rule (ruleId: 'NODE_ID_NAMESPACING'): every `node_types[i].type` must match the regex `^[a-z0-9-]+::[a-z0-9-]+$` (lowercase, hyphens, double-colon separator). Reject bare IDs like `'script'` or `'asset'`. Examples: `'movie-v1::script'` valid, `'podcast-v1::episode'` valid, `'script'` invalid (no namespace), `'Movie-V1::Script'` invalid (uppercase).

    The remaining three ruleIds are produced by mapping zod's built-in error codes to our SCREAMING_SNAKE vocabulary (do not write .refine for these — let zod detect them, then remap the error code in the catch path):
    - `MANIFEST_REQUIRED_FIELD` — emitted when zod reports a missing required field (zod issue code 'invalid_type' with 'required' message, or code 'missing_key' depending on zod v4)
    - `MANIFEST_TYPE_MISMATCH` — emitted when zod reports a type mismatch (code 'invalid_type' where the field exists but the value has the wrong type)
    - `MANIFEST_UNKNOWN_FIELD` — emitted by `.strict()` when zod reports an unrecognized key (zod v4 issue code 'unrecognized_keys')

    Implement the error-code remapping inside a `mapZodError(zodError, refinedRuleIds): ManifestValidationError[]` helper. The refinedRuleIds parameter is a map from field-path → ruleId for the custom .refine failures (so version + node type errors get their SCREAMING_SNAKE ruleIds instead of falling through to a generic type error). Read the zod v4 error structure (zodError.issues array with { code, path, message, expected, received }) and translate each issue to one ManifestValidationError with:
    - `ruleId`: from the remap (required/type-mismatch/unknown-field) or from refinedRuleIds if the path matches a .refine failure
    - `field`: `'root'` for root-level issues, or dotted-path like `'node_types[0].type'` for nested
    - `message`: human-readable, e.g., `"Node type 'script' is missing the required '<skill_id>::<type>' namespace prefix"`
    - `raw`: the original zod issue object (typed as `unknown` to match contract.ts)

    Export function `validateManifest(input: unknown): ManifestValidationResult`. Implementation:
    - Run `manifestSchema.safeParse(input)`.
    - If `result.success === true`: return `{ ok: true, value: result.data as SkillManifest }`.
    - If `result.success === false`: call `mapZodError(result.error, refinedRuleIds)` to produce `ManifestValidationError[]`, then return `{ ok: false, errors }`.

    Do NOT throw — always return the tagged union. Callers (Phase 30 REST API) will branch on `.ok`.

    Export the raw `manifestSchema` as a named export too (Plan 02's drift test will walk its `.shape`).

    Do NOT create an index.ts barrel — that is deferred per CONTEXT.md.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| manifest-author → validator | An external skill author (kais-movie-agent in OpenClaw, future podcast-v1, future third-party) submits a manifest JSON blob that crosses into platform-trusted memory via validateManifest(). The input is fully untrusted. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-28-01 | Tampering | validateManifest input | mitigate | zod `.strict()` on root + every nested object rejects unrecognized keys; no `any` passthrough; typed as `unknown` at entry |
| T-28-02 | Information Disclosure | ManifestValidationError.raw | accept | The `raw` field carries the original zod error object. zod errors do not echo the full input (only paths + expected/received types); acceptable for a single-tenant creative platform. If future logging surfaces input values, add redaction. |
| T-28-03 | Elevation of Privilege | SkillManifest interface | mitigate | CONTRACT-06 — the interface is purely a data shape. No methods, no functions, no executable code. A malicious manifest cannot invoke behavior because there is none to invoke. |
| T-28-04 | Tampering | node_types[].type field | mitigate | NODE_ID_NAMESPACING .refine() rejects bare IDs; format regex `^[a-z0-9-]+::[a-z0-9-]+$` is restrictive (lowercase, hyphens, double-colon only). Prevents path-traversal-style tricks in node type identifiers. |
| T-28-SC | Tampering | npm install (zod) | accept | zod v4.3.5 already in package.json and node_modules (verified). No new package install in this phase — no supply-chain gate needed. |

</threat_model>
