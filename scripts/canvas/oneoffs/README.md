# scripts/oneoffs/ — 一次性脚本约定

本目录存放**一次性修复/回填脚本**：为某一次历史数据问题而写、跑完即归档、
不应再进入常规运维流程的脚本。

## 什么算 one-off

满足以下任一特征的脚本应归到本目录，而不是 `scripts/` 根目录：

- 针对**某个具体历史事故/数据窗口**的修复（例如某日期前导入产生的空壳节点）；
- 源头契约已在代码中加固，**重复运行无必要甚至有风险**（可能用合成值覆盖更新数据）；
- 需要「显式审批 + DB 备份」才允许对生产数据执行；
- 保留价值在于**审计与可复现**，而非日常使用。

反面：会被管线/cron 反复调用的脚本（如同步、验证、常规回填）不属于 one-off。

## 命名

- 动词开头、描述这一次性动作：`backfill-<目标>.py`、`migrate-<目标>.js`。
- 不带日期后缀；运行时间写在 Docstring 运行记录里，而不是文件名里。

## Docstring 必填内容

每个 one-off 脚本头部 Docstring 必须包含：

1. **状态标记**：首行 `[DEPRECATED — <phase/date>]` 或等价的归档说明，
   写明该脚本为何诞生、上游契约在哪个阶段被加固、为何不应再跑。
2. **运行记录**：何时、对哪个 DB 跑过、影响行数与分解（修复多少 / 无法修复多少）、
   跑前备份文件位置、审计轨迹位置。
3. **警示语**：必须包含
   `Do NOT add to cron. Do NOT run against production data without explicit approval + DB backup.`
4. **背景与操作语义**：问题根因（及在代码中的修复点）、脚本对每个目标行的操作优先级、
   USAGE（默认 dry-run + `--apply` 写库）、明确声明不触碰哪些行。

可参考 `backfill-asset-descriptions.py` 的头部注释作为模板。

## 执行纪律

- 默认 dry-run，必须显式 `--apply` 才写库。
- 跑生产前：显式审批 + 全量 DB 备份，运行日志与跑后核验结果存档。
